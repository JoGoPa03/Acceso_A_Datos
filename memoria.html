¿Por qué no hay regla para el puerto 3306? MySQL escucha exclusivamente en la interfaz de loopback (127.0.0.1:3306), por lo que el tráfico JDBC nunca sale de la máquina. No es necesaria ninguna regla en el grupo de seguridad para el puerto 3306 porque la conexión entre la API y MySQL ocurre internamente. La administración remota se realiza a través de un túnel SSH, que aprovecha la regla del puerto 22.

3. Registro de decisiones

DecisiónAlternativa descartadaCriterio y requisito al que respondeConsecuencia
MySQL 8.4 MariaDB o PostgreSQL Es la opción por defecto del enunciado y la más documentada para el módulo. El driver mysql-connector-j es el estándar de referencia. Requisito: «elegir un SGBD relacional para la biblioteca». Compatibilidad total con los scripts SQL proporcionados; sin necesidad de adaptación.
t3.micro (1 GiB) t3.small (2 GiB) El profesor indicó que se usara t3.micro. Medí un consumo real de ~722 MiB de RAM entre MySQL y Java; con 1 GiB el sistema recurre ligeramente al swap (41 MiB), pero el rendimiento es aceptable para tráfico académico. Se configuró swap de 1 GiB como red de seguridad. Requisito: «una única máquina pequeña». Menor coste por hora; uso moderado de swap sin degradar el rendimiento perceptiblemente; riesgo de OOM si se aumenta la carga.
Requires=mysql.service Wants=mysql.service Con Requires, si MySQL se detiene, la API también se detiene, evitando que los clientes reciban respuestas parciales o errores 503 continuos. Con Wants, la API seguiría viva devolviendo 503. Para una biblioteca, es preferible un corte limpio: si la base de datos no está disponible, la API no puede cumplir ninguna petición útil. Requisito: «garantizar que todo vuelva a funcionar tras un reinicio». Una parada de MySQL arrastra la API; el administrador ve un solo problema en vez de dos servicios degradados.
bind_address = 127.0.0.1 bind_address = 0.0.0.0 MySQL no necesita escuchar en la red porque la API está en la misma máquina. Escuchar solo en loopback es la primera barrera de defensa en profundidad (la segunda es el grupo de seguridad sin regla para 3306). Requisito: «qué se expone a la red y qué no». MySQL es inaccesible desde fuera incluso si el grupo de seguridad se configurara mal. La administración remota requiere túnel SSH.
JdbcClient con DAO e interfaces JPA / Spring Data JPA El enunciado prohíbe expresamente JPA: «no añadas Spring Data JPA: introduce un ORM, que es el contenido del tema 3». JdbcClient permite un control total del SQL y cumple el patrón DAO con interfaces e implementaciones @Repository. Requisito: «el acceso a datos se programa con JDBC». Más código que con JPA, pero control total de las consultas, uso de parámetros con nombre y RowMapper explícitos.
innodb_buffer_pool_size = 256M Valor por defecto (128M) Con t3.micro y 908 MiB de RAM, el presupuesto de memoria es ajustado. 256M para el buffer pool deja margen para Java (-Xmx384m) y el sistema. Medido: MySQL usa ~275 MiB RSS, lo cual confirma que el ajuste es adecuado. Requisito: «repartir los recursos de forma explícita». MySQL puede mantener más índices y datos en memoria, reduciendo lecturas de disco. El conjunto MySQL + Java cabe en ~722 MiB sin OOM.
SELECT ... FOR UPDATE en PrestamoServicio Sin bloqueo de filas Dos peticiones simultáneas podrían prestar el último ejemplar dos veces si no se bloquean las filas del libro y el socio. El bloqueo pesimista en orden fijo (primero libro, luego socio) evita condiciones de carrera y deadlocks. Requisito: «las cinco reglas en orden, en una transacción con bloqueo de filas». Menor concurrencia teórica (las transacciones se serializan por libro/socio), pero integridad garantizada.
Usuario de sistema biblioteca sin shell Ejecutar la API como root o ubuntu Principio de privilegio mínimo: si un atacante explota una vulnerabilidad en la API, solo obtiene los permisos del usuario biblioteca, que no tiene shell ni directorio personal. Requisito: «si alguien llegara a comprometer la aplicación, solo obtendría los permisos de ese usuario». La API no puede modificar ficheros del sistema ni escalar privilegios.

4. Cuestiones de análisis

1. Presupuesto real de memoria

Con los datos de E12, la tabla de consumo real es:

ComponenteEstimación (tabla 3)Medido real

Java (API)~300 MiB194 MiB (RSS)

¿Funcionaría en una t3.micro? Sí, funciona. Con 908 MiB de RAM, el sistema usa ~722 MiB (80 %) y recurre ligeramente al swap (41 MiB, un 4 % del swap de 1 GiB). El OOM killer no ha actuado. Sin embargo, el margen es muy ajustado: no hay espacio para picos de carga. ¿Qué cambiaría y qué perdería? Reduciría innodb_buffer_pool_size a 128M y -Xmx a 256m, lo que liberaría ~256 MiB pero degradaría el rendimiento: MySQL haría más lecturas de disco y la JVM haría recolecciones de basura más frecuentes. Para un entorno de producción real, una t3.small (2 GiB) sería la elección correcta.

2. Dependencias entre servicios

Con Requires=mysql.service (configuración actual):

Al ejecutar sudo systemctl stop mysql, systemd también detiene biblioteca.service porque tiene Requires=mysql.service. Un cliente que intente conectar no recibe respuesta (connection refused en el puerto 8080). En journalctl -u biblioteca aparece que el proceso terminó con el código 143 (SIGTERM).

Con Wants=mysql.service:

Al detener MySQL, la API sigue viva. Las peticiones que necesitan la base de datos devuelven un error 503 Service Unavailable gracias al @RestControllerAdvice que captura DataAccessResourceFailureException. El endpoint /api/estado también devuelve 503 porque intenta ejecutar SELECT VERSION().

¿Qué comportamiento prefiero? Requires, por dos razones: (1) sin base de datos, la API de la biblioteca no puede cumplir ninguna función útil — todas las operaciones requieren datos; (2) un servicio detenido genera menos confusión que un servicio que responde con errores continuamente; el administrador ve un único problema en el panel de systemd en vez de un servicio «activo» que en realidad no funciona.

3. Defensa en profundidad

Las dos barreras que impiden conectar desde el aula al puerto 3306 son:

  1. Barrera 1 – MySQL bind_address: MySQL escucha solo en 127.0.0.1:3306 (loopback). Incluso si alguien pudiera enviar un paquete TCP al puerto 3306 de la instancia, MySQL no lo aceptaría porque no escucha en la interfaz de red ens5. Demostrado con E4 (ss -tlnp).
  2. Barrera 2 – Grupo de seguridad: No existe ninguna regla de entrada para el puerto 3306 en el grupo de seguridad. Los paquetes TCP al puerto 3306 se descartan antes de llegar a la instancia. Demostrado con E7 (Test-NetConnection al puerto 3306 devuelve TcpTestSucceeded: False).

¿Qué ocurriría si se quitara solo una? Si se cambiara bind_address a 0.0.0.0 pero sin abrir el puerto en el grupo de seguridad, MySQL aceptaría conexiones locales pero los paquetes externos seguirían bloqueados por AWS. Si se añadiera una regla para 3306 pero MySQL siguiera en loopback, los paquetes llegarían a la instancia pero MySQL los rechazaría. Solo quitando ambas barreras sería posible la conexión directa desde fuera.

4. Privilegio mínimo

Impacto de una inyección SQL según el usuario de MySQL:

UsuarioQué podría hacer un atacante
biblioteca_appSolo SELECT, INSERT, UPDATE, DELETE en las tablas de biblioteca. No puede DROP TABLE, CREATE TABLE ni acceder a otras bases de datos. El daño se limita a leer o modificar datos de la biblioteca.
biblioteca_adminALL PRIVILEGES sobre biblioteca: podría DROP TABLE, ALTER TABLE, crear o eliminar índices. Podría destruir el esquema completo, pero no acceder a otras bases de datos ni a la configuración de MySQL.
rootControl total: DROP de cualquier base de datos, leer archivos del sistema con LOAD_FILE(), modificar usuarios y permisos, potencialmente ejecutar comandos del sistema.

Prueba en DBeaver: al conectar como biblioteca_app e intentar DROP TABLE prestamo, MySQL devuelve: ERROR 1142 (42000): DROP command denied to user 'biblioteca_app'@'localhost' for table 'prestamo'. Esto confirma que el principio de privilegio mínimo funciona.

5. Concurrencia

Escenario sin SELECT ... FOR UPDATE:

Supongamos que el libro con id=4 tiene 2 ejemplares y 1 préstamo abierto (1 disponible). Dos peticiones simultáneas de préstamo (socio 1 y socio 2) para el libro 4:

  1. Hilo A: SELECT ejemplares FROM libro WHERE id = 4 → lee 2 ejemplares
  2. Hilo B: SELECT ejemplares FROM libro WHERE id = 4 → lee 2 ejemplares
  3. Hilo A: SELECT COUNT(*) FROM prestamo WHERE libro_id = 4 AND fecha_devolucion IS NULL → lee 1 préstamo abierto → 2 - 1 = 1 disponible → procede
  4. Hilo B: SELECT COUNT(*) FROM prestamo WHERE libro_id = 4 AND fecha_devolucion IS NULL → lee 1 préstamo abierto → 2 - 1 = 1 disponible → procede
  5. Hilo A: INSERT INTO prestamo ... → éxito, ahora hay 2 préstamos
  6. Hilo B: INSERT INTO prestamo ... → éxito, ahora hay 3 préstamos — ¡pero solo hay 2 ejemplares!

Cómo se evita: en PrestamoServicio.java, línea 58, el método crear() usa SELECT id, ejemplares FROM libro WHERE id = :id FOR UPDATE. Esto bloquea la fila del libro para otras transacciones. El hilo B queda esperando hasta que el hilo A haga commit, momento en el cual el hilo B lee el estado actualizado (2 préstamos abiertos) y detecta que no hay disponibilidad, devolviendo 409. El bloqueo del socio (línea 65) evita también condiciones de carrera en el conteo de préstamos del socio.

6. Recomendación al cliente

Comparación de la arquitectura actual con una separación en Amazon RDS:

AspectoArquitectura actual (colocalización)EC2 + Amazon RDS
DisponibilidadPunto único de fallo: si la instancia cae, se pierden API y datos. Recuperación manual.RDS ofrece Multi-AZ con failover automático. La caída de la instancia EC2 solo afecta a la API, no a los datos.
MantenimientoActualizaciones de MySQL, backups y monitorización son responsabilidad del administrador.RDS gestiona parches, backups automáticos, réplicas de lectura y monitorización con CloudWatch.
SeguridadMySQL y la API comparten la misma máquina: una vulnerabilidad en uno compromete al otro.Aislamiento de red: MySQL en subred privada, API en pública. Menor superficie de ataque.
Coste~0,012 $/h (t3.micro). Todo en una máquina.~0,012 + ~0,034 $/h (db.t3.micro RDS). Triple de coste mínimo.

Recomendación: Con la previsión de multiplicar por diez los socios, la arquitectura actual no escalará: la memoria compartida es ya ajustada, y el mayor tráfico agotará los recursos. Recomiendo migrar a RDS con una instancia db.t3.micro inicialmente (que puede escalar verticalmente) y mantener la EC2 solo para la API. El coste extra (~0,034 $/h) es asumible frente a las ventajas: backups automáticos, failover Multi-AZ, y la posibilidad de añadir réplicas de lectura si el tráfico lo requiere. Como paso intermedio, se podría empezar con RDS Single-AZ para reducir coste y activar Multi-AZ cuando la carga lo justifique.

5. Incidencias encontradas y resolución

IncidenciaResolución
SSH: Permission denied con la clave labsuser.pem La clave labsuser.pem descargada del Learner Lab no era la correcta para esta instancia. Se probó con la clave alternativa disponible, que fue aceptada. Verificado con ssh -v que la autenticación por clave pública funcionaba.
JAVA_HOME no configurado en Windows El Maven wrapper fallaba con «No compiler is provided in this environment». Se configuró JAVA_HOME apuntando a C:\Program Files\Eclipse Adoptium\jdk-21.0.13.9-hotspot tanto en la sesión de PowerShell como en la variable de entorno del usuario.
mysqldump: aviso de privilegio PROCESS El script de backup mostraba «Access denied; you need PROCESS privilege for tablespaces». Es solo un aviso informativo: el volcado de datos se completa correctamente sin este privilegio. El usuario biblioteca_admin tiene ALL PRIVILEGES sobre el esquema biblioteca pero no el privilegio global PROCESS.
Servicio biblioteca no habilitado inicialmente Tras instalar el servicio con systemctl daemon-reload, el servicio arrancaba pero no estaba habilitado para el arranque automático. Se solucionó con sudo systemctl enable biblioteca. Tras sudo reboot, ambos servicios (mysql y biblioteca) arrancaron correctamente.
Memoria ajustada en t3.micro Con MySQL y Java compitiendo por 908 MiB de RAM, el sistema recurría al swap. Se optimizó: innodb_buffer_pool_size=256M (en vez de 384M o más), -Xmx384m (en vez de 512m), max_connections=40, performance_schema=OFF. Con estos ajustes, el uso de swap se mantiene en 41 MiB y el OOM killer no ha actuado.
